## FIXED (verified working)

### P0 — these were breaking the product for real users

**1. Every fare was priced for the wrong day, every evening.** `upcomingFridayISO` built a local Date then formatted with `toISOString()` (UTC). For any US user browsing after ~4pm PT / 7pm ET, the date rolled forward — Travelpayouts was queried for **Saturday**, the flight cache keyed on Saturday, and the Aviasales booking deep-link pre-filled Saturday, all labeled "Fri." Verified before/after: Friday 8:30pm PDT returned `2026-07-25`, now returns `2026-07-24`. Fixed with a `localISODate()` helper at all three call sites (`upcomingFridayISO`, `getFlightDate`, `scoreWeekend`'s `weekendFriISO`).

**2. Cloud sync destroyed data on second-device sign-in.** `pullNow` wrote the server blob into localStorage and dispatched `peakly-sync-pulled` — **nothing listened**. `useLocalStorage` only reads storage in its initializer, so React state stayed pre-pull (usually empty); the next heart-tap serialized that stale state over the fresh cloud data and pushed it. 20 saved venues → 1. Added a `peakly-sync-pulled` listener inside `useLocalStorage` that re-reads and re-renders.

**3. The refresh button called a function that doesn't exist.** `onRefresh={() => fetchAllWeather(false)}` — the real name is `fetchInitialWeather`. Every pull-to-refresh and header refresh tap threw a ReferenceError. This is the exact recovery path the "conditions unavailable — pull to refresh" banner instructs users to use, so cold-start recovery was dead. One-token fix.

**4. Guaranteed ErrorBoundary crash in WishlistsTab (2 sites).** `alertedIds`/`onAlertToggle` referenced in JSX but never passed as props — the identical bug class as the old `flightsLoading` P0, masked only because the Trips tab is hidden. Would detonate the day Wishlists/Trips is un-hidden. Removed the out-of-scope attributes (ListingCard already guards both).

### P1

**5. The two-weekend feature was silently off in production.** The proxy requested `forecast_days=7` while the client expects 14 and tries the proxy *first* — so whenever the VPS is healthy (i.e. always), `scoreWeekend` could never see the second weekend. Phase C only worked when infrastructure was broken. Proxy now requests 14. **Requires VPS redeploy to take effect.**

**6. Saturday/Sunday fused this-weekend conditions with next-Friday's fare.** The `weekendWhich === "next"` guard caught one direction; on Sat/Sun `upcomingFridayISO` skips to next Friday while the scored window stays the in-progress weekend, so "Strong deal" claims fused conditions and prices from different trips. Added a date-equality guard; verified it now returns `score: null` on a Saturday.

**7. Marine fetch requested 14 days, above the model's horizon** — risking a 400 that silently kills the water-temp gate for every beach venue (the exact failure mode of the old `ocean_temperature_max` bug). Client + proxy now request 10.

**8. Safe-area insets were a no-op on iOS.** The viewport meta lacked `viewport-fit=cover`, so every `env(safe-area-inset-*)` in the app resolved to 0 — header under the notch, tab bar under the home indicator, in both the installed PWA and the Capacitor build. One attribute.

**9. First-time visitors got force-reloaded mid-session.** The `controllerchange` listener can't distinguish "new deploy" from "first SW install" (`clients.claim()` fires it too), so every brand-new user got a full page reload seconds in — exactly the launch-day audience. Now only reloads when an existing controller was replaced.

**10. Alert deletion never worked.** CORS `Access-Control-Allow-Methods` omitted DELETE, so the preflight blocked every delete; the client's `.catch(() => {})` hid it. Deleted alerts kept polling server-side and would fire push forever once APNS goes live.

**11. Rate limiter was trivially bypassable.** Took the *first* `X-Forwarded-For` entry, which the client controls (Caddy appends the real IP last). A random XFF per request = unlimited rate + unbounded `_rateMap` growth. Now takes the last entry.

**12. iOS CORS origin missing.** `capacitor://localhost` wasn't in the allowlist — every proxy call from the native app would have been blocked. This would have looked like "the iPhone app can't load weather" with no obvious cause.

**13. Stale-closure bug:** `quickToggleAlert` read `cloudSync` without depending on it, so users who signed in mid-session kept getting the sign-up modal from card bells. Added the dep.

**14. Map opened empty on first use.** The marker effect depended on `[listings]` but bails while Leaflet is still loading, and never re-ran once ready. Added `leafletReady` to the deps.

**15. Misc:** rules-of-hooks violation in `ProfileSyncSection` (early return before hooks — guard moved below); `a.locations.length` crash on legacy alerts (2 sites); `wind_speed_10m_max[i]` unguarded array access; iOS push-promise copy in `AccountNudgeBanner` (the one banner the June copy-honesty pass missed — an App Store reviewer with 3 saves would see a notification promise iOS can't keep).

## NOT fixed — decisions or non-trivial

- **APNS will deliver zero pushes when wired.** Two independent defects in `server/proxy.js`: the ES256 JWT uses DER encoding (Apple requires raw R‖S — needs `dsaEncoding: 'ieee-p1363'`), and `firePush` uses global `fetch`, which is HTTP/1.1-only while APNs requires HTTP/2 (needs the `http2` module). Not fixed because push is deliberately gated off for iOS v1 — but **do not wire APNS without fixing these first.**
- **Alerts API is unauthenticated with guessable IDs** (`Date.now()`): anyone can delete others' alerts, hijack one by re-POSTing the id with their own push token, or fill all 10,000 slots. Fix is client-side UUIDs + an ownership check. Tolerable at ~0 MAU, must fix before push ships.
- **Duplicate venue:** `tahoe` and `palisades-tahoe` are the same resort (coords 120m apart). Recommend deleting `palisades-tahoe` and bumping `.venue-baseline` to 357.
- **Trans-dateline day misalignment:** `timezone=auto` returns venue-local days while indices come from user-local "today," so Asia/Pacific venues are off by one day for US evening users. Proper fix is anchoring indices by ISO date lookup in `wx.daily.time` rather than by offset — a ~15-line change to `weekendDayIndices`/`scoreOneWeekend` that deserves its own test pass.
- **Low-confidence scores rank undiscounted** in the grid sort (carousels filter correctly). Mid-week users can never see a next-weekend pick, because confidence is graded by the window's *worst* day.
- **BASE_PRICES covers 134/358 venues** — 63% of the catalog runs deal math on coarse estimates, including CUN, MIA, LAX, and the whole Southern-hemisphere ski batch.
- **`poolPrimary` is dead** — documented in CLAUDE.md, implemented in `scoreVenue`, set on zero venues.
- **Two dead splash/error traps:** the splash is only dismissed inside App's first effect, so any pre-mount failure leaves users staring at it forever (the Babel-fallback "Retry" UI renders *underneath* it); and the global "Unexpected token" handler can nuke the running app if a stray `JSON.parse` throws post-mount.
- **`peakly-native/` is a second, abandoned Expo app** — archive it before someone builds the wrong project.

## Verdict

The scoring core is genuinely well-built — units are right, nulls can't produce NaN, the concurrency semaphore is sound, and the SQL `delete_user()` is correctly scoped to the caller with no injection path. The failures clustered at the **boundaries**: dates crossing UTC, the client/proxy contract, and props crossing component scopes. Three of the four P0s would have hit users on day one of any launch, and two of them (wrong fare dates, dead refresh button) were invisible to the existing smoke tests because headless runs have no weather and never touch the calendar.

**Before deploy:** commit + push, then redeploy the VPS (`forecast_days` + CORS + rate limiter are all server-side and inert until then).
