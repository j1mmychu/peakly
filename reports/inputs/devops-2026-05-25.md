### P1 — SRI Missing on 4 CDN Scripts (Day 21)

Leaflet already has SRI (`sha256-p4Nx...`). React, ReactDOM, Babel, and Supabase do not. A CDN compromise on any of these delivers arbitrary JS to every Peakly user. This is a supply-chain risk, not a theoretical one — unpkg and jsdelivr have had CDN integrity incidents.

**Exact fix — add these `integrity` attributes to `index.html`:**

> ⚠️ The hashes below must be verified against the actual CDN responses before deploying.  
> Generate them with:  
> ```bash
> curl -s https://unpkg.com/react@18.3.1/umd/react.production.min.js | openssl dgst -sha384 -binary | openssl base64 -A
> curl -s https://unpkg.com/react-dom@18.3.1/umd/react-dom.production.min.js | openssl dgst -sha384 -binary | openssl base64 -A
> curl -s https://unpkg.com/@babel/standalone@7.29.4/babel.min.js | openssl dgst -sha384 -binary | openssl base64 -A
> curl -s https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.106.0/dist/umd/supabase.min.js | openssl dgst -sha384 -binary | openssl base64 -A
> ```
> Then replace `<HASH_HERE>` in the snippet below:

```html
<!-- React 18 + ReactDOM (UMD) -->
<script crossorigin
  src="https://unpkg.com/react@18.3.1/umd/react.production.min.js"
  integrity="sha384-<HASH_HERE>"
></script>
<script crossorigin
  src="https://unpkg.com/react-dom@18.3.1/umd/react-dom.production.min.js"
  integrity="sha384-<HASH_HERE>"
></script>

<!-- Supabase JS (UMD) -->
<script
  src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.106.0/dist/umd/supabase.min.js"
  integrity="sha384-<HASH_HERE>"
  crossorigin="anonymous"
></script>

<!-- Babel Standalone -->
<link rel="preload"
  href="https://unpkg.com/@babel/standalone@7.29.4/babel.min.js"
  as="script" crossorigin />
<script
  src="https://unpkg.com/@babel/standalone@7.29.4/babel.min.js"
  integrity="sha384-<HASH_HERE>"
  crossorigin="anonymous"
></script>
```

**Note on Babel + SRI:** Babel's inline `eval` requires `unsafe-eval` in CSP. SRI on the script tag itself is compatible with inline eval — SRI verifies the *script file*, not what it executes. These are orthogonal concerns.

**Estimated time: 20 minutes (10 min to generate hashes + 10 min to apply + test).**

## 7. What Breaks First at Scale

Same as May 22 diagnosis — nothing has changed on the infrastructure side.

1. **Open-Meteo shared-IP rate limit.** 100+ concurrent users on GitHub Pages' shared IPs → Open-Meteo bans the IP range → `scoreVenue` silently returns 0 for all venues → Explore grid shows all "N/A — 0" scores → users bounce. No error in Sentry because `scoreVenue` handles null weather gracefully (floors to 0, doesn't throw). You find out from a Reddit comment. The server proxy is written and tested. **One SSH command prevents this.**

2. **proxy.js in-memory rate-limit Map OOM on 10K MAU.** The `_rateMap` cleanup runs every 5 minutes, but between cleanups at 60K req/min (10K MAU × 6 req/min avg), the Map can hold 10K+ entries × ~200 bytes = ~2MB. Fine on 1GB RAM. At 50K MAU it's 10MB between cleanups on a 1GB droplet with Node also holding the in-memory weather cache (4000-entry LRU × ~2KB each = ~8MB). Combined peak: ~20MB. Still fine. **Upgrade droplet to 2GB ($12/mo) before 25K MAU** — takes 5 minutes in the DO console with zero downtime via live resize.

3. **agent sequencing race condition** (new finding, evidenced this run). Content and DevOps agents commit to the same files on the same day. Content ran 1h after DevOps on May 22 and invalidated the cache buster. May 20 DevOps reverted May 18 dep updates. Without explicit agent-to-agent coordination, each run treats HEAD as ground truth and may clobber the previous run's intentional changes. Fix options:
   - Schedule DevOps *last* in the daily chain (after 17:30 briefing)
   - Add `git log --oneline -3 -- index.html app.jsx` to the start of DevOps prompt
   - Use a `.cache-version` sentinel file so only the agent that owns it changes the version
