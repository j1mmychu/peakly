### Recurring Structural Problem: Agent Queue Ordering

DevOps runs at 14:00, Content runs at 15:00. DevOps bumps the cache buster; Content changes `app.jsx` an hour later. The buster is stale by 15:18 every day Content has code changes. 

**Fix (2 options):**
1. Run DevOps last in the daily queue (after 17:00) so the buster covers all agent edits that day.
2. Move the cache-buster bump to `scripts/auto-push.sh` — auto-bump on every `app.jsx` edit by any agent.

Option 2 is cleaner. `auto-push.sh` already runs on every Edit/Write. Add a 4-line block that reads current buster, checks date, and bumps if it doesn't match today:

```bash
# In scripts/auto-push.sh, after the dirty-check, before git add:
TODAY=$(date +%Y%m%d)
CURRENT=$(grep -o 'PEAKLY_BUILD = "[0-9a-z]*"' app.jsx | grep -o '"[0-9a-z]*"' | tr -d '"')
if [[ "$CURRENT" != "${TODAY}a" && "$CURRENT" < "${TODAY}" ]]; then
  sed -i "s/PEAKLY_BUILD = \"[^\"]*\"/PEAKLY_BUILD = \"${TODAY}a\"/" app.jsx
  sed -i "s/CACHE_NAME = \"peakly-[^\"]*\"/CACHE_NAME = \"peakly-${TODAY}a\"/" sw.js
  sed -i "s/app\.jsx?v=[0-9a-z]*/app.jsx?v=${TODAY}a/" index.html
fi
```

### P2-A — Missing SRI on 5 of 7 CDN Scripts (persistent, day 22)

Leaflet has SRI. React, ReactDOM, Babel, and Supabase JS do not. A compromised unpkg/jsdelivr CDN could serve malicious JS with full DOM access to all user data. Medium risk at current traffic; high risk post-Reddit-launch.

Note: Adding SRI to Babel Standalone requires careful testing — Babel uses `eval()`-like mechanisms that CSP + SRI can interact with unexpectedly. Test on a dev copy first.

**Exact fix for `index.html` (generate hashes via `openssl dgst -sha384 -binary <file> | openssl base64 -A`):**

```html
<!-- React 18.3.1 -->
<script crossorigin src="https://unpkg.com/react@18.3.1/umd/react.production.min.js"
        integrity="sha384-GENERATE_HASH_BEFORE_ADDING"
        crossorigin="anonymous"></script>

<!-- ReactDOM 18.3.1 -->
<script crossorigin src="https://unpkg.com/react-dom@18.3.1/umd/react-dom.production.min.js"
        integrity="sha384-GENERATE_HASH_BEFORE_ADDING"
        crossorigin="anonymous"></script>

<!-- Supabase JS 2.45.4 -->
<script src="https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.45.4/dist/umd/supabase.min.js"
        integrity="sha384-GENERATE_HASH_BEFORE_ADDING"
        crossorigin="anonymous"></script>
```

### P2-B — No CSP Meta Tag (persistent, day 22)

No `Content-Security-Policy` header or `<meta http-equiv="Content-Security-Policy">`. Inline `<style>` and Babel's JSX eval require permissive CSP — but even a partial policy (blocking `data:` URIs, `object:`, etc.) reduces attack surface.

**Important:** Babel Standalone transforms JSX by calling `eval()` internally. Any CSP that includes `'unsafe-eval'` is effectively no-ops'd for script injection anyway. This means CSP buys less here than in a compiled app. Still worth adding `frame-ancestors 'none'` to prevent clickjacking:

```html
<meta http-equiv="Content-Security-Policy"
      content="frame-ancestors 'none'; object-src 'none';">
```

This is the safe subset that won't break Babel. The full CSP (blocking `unsafe-eval`) requires eliminating Babel client-side transpilation — which means a build step, which is out of scope for v1.

**Largest single bottleneck: Babel Standalone at ~277 KB gzipped (~1.1 MB raw).** This is the structural cost of the no-build-step architecture. It must download, parse, and execute before any JSX can run. On a 4G mobile connection (10 Mbps down), 277 KB = ~0.2s additional parse time after download — acceptable but non-trivial.

The splash screen hides this: the CSS-only animated loader renders immediately from `<style>` in `<head>` while Babel loads. This is already in place and working.

**Second largest bottleneck: 150 simultaneous Open-Meteo calls on first render (without proxy).** Each call adds ~300-800ms RTT to the score pipeline. First batch of 50 fires immediately; venues appear after those 50 resolve. The 1s inter-batch delay is polite but means the full 100-venue grid takes ~2s+ to fully populate on first load. With the proxy cache, this collapses to near-instant after the first user warms it.

## What Breaks First at Scale

**The single most likely failure at any meaningful traffic** is Open-Meteo rate limiting. At 67 DAU the free tier is saturated without the proxy. At 500 DAU, venues start returning 0 scores for the majority of users. The app doesn't fail visibly — it just shows blank scores, which looks like "the app doesn't work." Users churn. This is catastrophic at launch.

**Prevention: Deploy the VPS proxy. One SSH command. 90 seconds. It has been 22 days.**

After that, the next failure point is Supabase free tier (500MB database) when cloud sync users accumulate data. The `user_data` table stores large JSON blobs. At 1K synced users × ~50KB per user = 50MB — well within limits. At 10K synced users = 500MB — hitting the ceiling. Mitigation: trim `peakly_errors` and `peakly_perf` from sync (already excluded per SYNCED_KEYS). At 10K MAU, upgrade to Supabase Pro ($25/month) before hitting the ceiling.
