## P0 — APNS .p8 + env vars (App Store launch blocker)

`server/proxy.js` checks for `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`, `APNS_KEY_PATH` (proxy.js:442). Until these are set, `apnsConfigured()` returns false and the polling worker logs but never delivers a push. App Store reviewers will flag the alerts feature as non-functional.

Runbook is at `peakly-native/PUSH_SETUP.md`. Concrete steps Jack still needs to do, in order:

1. Apple Developer console → Keys → "+" → name "Peakly Push" → enable "Apple Push Notifications service (APNs)" → Continue → Register → **download the `.p8` file (one-time)** and note Key ID.
2. SCP the .p8 to the VPS:
   ```bash
   scp ~/Downloads/AuthKey_<KEYID>.p8 root@198.199.80.21:/opt/peakly-proxy/secrets/
   ssh root@198.199.80.21 'chmod 400 /opt/peakly-proxy/secrets/AuthKey_*.p8'
   ```
3. Add env vars (PM2 ecosystem file or `pm2 set`):
   ```bash
   ssh root@198.199.80.21 'cd /opt/peakly-proxy && \
     pm2 set peakly-proxy:APNS_KEY_ID "<KEYID>" && \
     pm2 set peakly-proxy:APNS_TEAM_ID "<TEAMID>" && \
     pm2 set peakly-proxy:APNS_BUNDLE_ID "com.peakly.app" && \
     pm2 set peakly-proxy:APNS_KEY_PATH "/opt/peakly-proxy/secrets/AuthKey_<KEYID>.p8" && \
     pm2 set peakly-proxy:APNS_PROD "true" && \
     pm2 set peakly-proxy:ALERTS_TEST_ENABLED "true" && \
     pm2 restart peakly-proxy'
   ```
4. Verify: `curl -sS https://peakly-api.duckdns.org/health | grep -iE 'apns'` should show `"apns_configured": true`.
5. Once App Store review is done, set `ALERTS_TEST_ENABLED=false` to disable the test-fire endpoint.

**Risk:** the .p8 is a credential. Make sure `/opt/peakly-proxy/secrets/` is in `.gitignore` on the VPS clone (already covered by `*.p8` in repo `.gitignore`, but the VPS path is outside the repo — verify the file isn't accidentally inside the working tree).

## What breaks first at scale

Two ceilings, listed in order they'll bite:

1. **VPS RAM at ~10K registered alerts** — `_alerts` Map is in-memory, polling worker iterates all alerts every 30 min. At 10K alerts × ~500 bytes each = 5 MB Map. Fine. The bigger pressure is the polling fetch: groups by venue lat/lon (good — reuses `_wxCache`), but at 10K unique venues you're hitting Open-Meteo 10K calls / 30 min = ~5.5/sec sustained. Open-Meteo's free tier is 10K calls/day per IP (CDN-cached, but still a published soft cap). Move to commercial tier (€29/mo for 100K calls/day) before 1K active venues with alerts.

2. **In-memory data loss on `pm2 restart`** — `_alerts` Map and `_wxCache` reset on every proxy restart. Cache reset is fine (rebuilds from upstream). Alerts reset is silent data loss for users — every PM2 restart silently un-registers everyone's alerts. Now that the polling worker exists, this is a real bug, not a theoretical one. Current `known-skipped.md` entry for "_alerts Map persist to disk" should re-escalate next run if VPS confirms-redeployed; file-backed JSON in `server/data/alerts.json` is the documented fix.
