## Explicit Product Decisions — June 9

**Decision 1 (NEW GATE): The auto-push invariant guard + cron backstop is now a launch gate, not a "mitigation."**
v52 called this a recommended safeguard. In one day it caused two production-affecting failures. That promotes it. Before any Reddit post, two things land:
- **Backstop:** `45 17 * * * cd ~/peakly && bash scripts/auto-push.sh` in Jack's local crontab (after the 17:30 briefing slot), so agent writes actually commit. Two-minute install — and it's the fix for GEAR, the 134 venues, *and* the stale cache stamp simultaneously.
- **Guard:** before `auto-push.sh` commits `app.jsx`, refuse if `grep -c GEAR_ITEMS` drops, brace balance goes uneven, or the cache stamp regresses. A revenue stream should not be able to die into an unlabeled commit. DevOps owns the diff; PM is stating it's required, not optional.

Without this, every fix below gets re-stripped or never ships. **This is the new top of the launch checklist.**

**Decision 2: RESTORE GEAR_ITEMS — but only after the guard (Decision 1), or formally CUT Amazon.**
This stream has now been silently removed *twice* (pre-05-24, and again June 7). Restoring it a third time into an unguarded pipeline is just scheduling the fourth removal. So: land the guard, then `git`-restore the 6-key block from `9656c6b~1` (confirmed intact), re-verify `grep -c GEAR_ITEMS`, bump cache, commit with a *real* message. If Jack would rather cut Amazon for v1, fine — then update CLAUDE.md's Revenue Model to **$7.58/1K MAU** and drop the Amazon row. Either way the shared brain stops claiming $4.48 from code that doesn't exist. Not "we'll see."

**Decision 3: DEFER the 134-venue batch. Do NOT ship it into the launch build.**
It's structurally clean (DevOps confirms brace-even, no dup IDs, all 58 airport codes present), but it is the wrong thing to ship right now for three reasons: (1) it violates the standing pre-launch freeze — an overnight agent batch should not redefine launch scope by sitting in the working tree; (2) it nearly **doubles the venue set (156 → ~290)**, which DevOps notes pulls the Open-Meteo free-tier throttle ceiling *closer* — on the direct-Open-Meteo path with the proxy cache still undeployed, that worsens the exact spike problem the VPS gate exists to solve; (3) it hasn't been content-reviewed (photos, names, overlap with existing 156). Hold it on a branch. It ships **after** VPS verification, folded into the June 10 sprint with review — never as an uncommitted surprise before a Reddit post.

**Decision 4: Jack renews the GitHub PAT this week. Hard deadline June 15.**
Six days out. `peakly-token-renewal` is watching, but the renewal is a manual Jack action. If it expires, push breaks and every fix above is stuck regardless of the pipeline work.

## One Product Risk Nobody Is Talking About

**Launch scope is now an emergent property of an unsupervised pipeline, not a human decision.**

What's in the launch build is currently determined by what the agents happened to leave in (or strip from) the working tree at 20:51 last night — not by anyone choosing it. GEAR_ITEMS left the product because three `auto:` commits removed it and nobody decided that. 134 venues are *out* of the product because the hook didn't fire and nobody decided that either. In both cases the deciding actor was a shell script's catchment radius, and the human found out via a grep the next day.

That's the real risk: not GEAR, not the venues — those are symptoms. The risk is that we are about to point Reddit traffic at a build whose contents no one has deliberately approved. Decision 1 (guard + backstop) is the minimum that puts a human back in the loop before launch. Until it lands, "what ships" is a question we can only answer by reading the diff each morning and hoping — and that is not a launch process.
