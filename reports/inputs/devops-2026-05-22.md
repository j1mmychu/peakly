### P1 — No SRI on React, ReactDOM, Supabase, Babel (Day 18, Unresolved)

Only Leaflet has `integrity=` hashes. The four largest scripts — React (43KB gz), ReactDOM, Supabase (~80KB gz), and Babel Standalone (~350KB gz) — load with no integrity check. A compromised unpkg or jsdelivr CDN delivers arbitrary JavaScript into every session before Sentry has a chance to fire.

**Generate hashes — run once from any machine:**
```bash
REACT_HASH=$(curl -s https://unpkg.com/react@18.3.1/umd/react.production.min.js | openssl dgst -sha384 -binary | openssl base64 -A)
DOM_HASH=$(curl -s https://unpkg.com/react-dom@18.3.1/umd/react-dom.production.min.js | openssl dgst -sha384 -binary | openssl base64 -A)
BABEL_HASH=$(curl -s https://unpkg.com/@babel/standalone@7.24.7/babel.min.js | openssl dgst -sha384 -binary | openssl base64 -A)
SUPA_HASH=$(curl -s https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.45.4/dist/umd/supabase.min.js | openssl dgst -sha384 -binary | openssl base64 -A)
echo "React:    sha384-$REACT_HASH"
echo "ReactDOM: sha384-$DOM_HASH"
echo "Babel:    sha384-$BABEL_HASH"
echo "Supabase: sha384-$SUPA_HASH"
```

**Add `integrity=` + `crossorigin="anonymous"` to all 4 scripts in index.html.** Test in browser immediately after — SRI blocks load if the CDN serves different bytes. **Time: 20 min.**

### P2 — No Content Security Policy (Day 18, Unresolved)

GitHub Pages cannot set HTTP headers; meta tag only. Babel requires `'unsafe-eval'` which limits the protection scope, but blocking unknown origins still raises the bar considerably.

**Add to `<head>` before the Sentry `<script>` tag:**
```html
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self' 'unsafe-eval'
    https://unpkg.com
    https://cdn.jsdelivr.net
    https://js.sentry-cdn.com
    https://plausible.io;
  style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
  font-src https://fonts.gstatic.com;
  img-src 'self' https://images.unsplash.com data: blob:;
  connect-src 'self'
    https://peakly-api.duckdns.org
    https://api.open-meteo.com
    https://marine-api.open-meteo.com
    https://marine.open-meteo.com
    https://plausible.io
    https://wsoqcfwkvvemtlddcgfc.supabase.co
    https://o4511108649058304.ingest.us.sentry.io;
  frame-ancestors 'none';
">
```

Test that Babel inline eval still works, Supabase magic-link redirect works, and Plausible fires. **Time: 25 min.**

## 7. What Breaks First at Scale

Open-Meteo client-side is the structural failure and it's been fixable for 18 days. The sequence:
1. Reddit/HN traffic spike → 200 concurrent users → 200 × 265 = 53,000 calls in minutes
2. Open-Meteo rate-limits the GitHub Pages shared IPs (you share ~50 IPs with thousands of other Pages sites)
3. `fetchWeather` returns null, `scoreVenue` floors to 0, all venues display "N/A — 0" scores
4. Explore feed becomes meaningless. Users bounce. Plausible shows a spike then a cliff.
5. You have no Sentry alert because `scoreVenue` doesn't throw — it just returns bad data
6. You find out from a Reddit comment two hours later

The server-side weather proxy in proxy.js is written, tested, and waiting. **One SSH command deploys it.** Every day it stays undeployed is a day the app is one traffic event away from public failure.

Second break point: in-memory rate limiter in proxy.js (line 21–45). It's a `Map()` that grows unbounded except for the 5-minute cleanup interval. At 10K MAU with 60 req/min/IP, the Map can hold 10K+ entries between cleanups. On the 1GB VPS, sustained 10K MAU will OOM. Fix: upgrade to 2GB droplet ($6/mo more) before 10K MAU — takes 5 minutes in the DO console.
